# 变更工作流

把已经明确的变更目标推进到可验证结果。流程力度取决于风险和交接需要，不由文件数量决定。用户明确要求与项目适用规则优先于本技能的默认建议；已有授权和偏好在后续步骤中继续有效。

## 开始工作

- 阅读适用的 `AGENTS.md`、项目入口和相关实现。按需查找测试、验收标准及已有计划，不为小改动遍读整个仓库。
- 用 `git status` 和相关差异确认起点，区分已有改动与本次任务。非 Git 项目直接检查相关文件，不把建立仓库当作前置步骤。
- 明确期望行为或验收结果，再开始修改。缺少信息时，先完成不依赖答案的工作；只对会实质影响范围、正确性或不可逆操作的问题澄清。普通实现选择可自行决定，不逐步请求批准。

## 选择合适的记录力度

| 情况 | 默认做法 |
| --- | --- |
| 目标明确、影响局部、容易回退，例如文字、样式或小范围修复 | 在对话中简述动作后实施，不额外创建计划文件 |
| 多个相关文件，但可以在当前任务中清楚完成 | 保留简短步骤和验证记录；不因文件较多就强制落盘计划 |
| 跨阶段、需要交接、存在重要决策，或涉及接口、数据迁移等较高风险 | 复用已有计划；确实需要时按项目惯例建立简短计划 |

用户或项目要求计划文件时遵循该要求。没有约定时可使用 `docs/plans/<feature>.md` 和 [精简计划模板](references/plan-template.md)，删除无关部分，不填满一套空栏目。

计划是上下文记录，不高于最新用户要求或已确认的代码事实。新证据推翻旧假设时，更新相关决策并简短说明原因；日常实现调整不需要用户重新批准。继续使用旧格式的计划时，读取其中的 `Decisions`、`Progress`、`Resume Notes` 等内容，无需为统一格式重写。

## 实施与验证

先选择能证明目标行为的验证方式，再进行修改：

- 可稳定复现的缺陷，优先复现或补有价值的回归测试，再修复原因。已有测试覆盖时可直接复用。
- 新行为与复杂边界使用能区分正确和错误结果的测试；涉及持久化、迁移或兼容性时检查已有数据与失败路径。
- 可逆、低风险的文字、样式、配置等改动采用合适的检查，如格式校验、构建、链接检查或实际查看。不要为了流程增加只重复实现的测试。
- 无法复现或测试环境受限时，记录已经尝试的证据和实际限制，使用仍能回答问题的检查；不能把推测或未执行的命令写成验证通过。

改动围绕目标，保留必要的兼容行为，不顺手做无关重构或增加臆测性框架。已有未提交工作是协作上下文，不是必须清空的障碍；保留他人的文件改动和暂存状态，必要时按差异片段处理。不要为了获得“干净环境”擅自丢弃、覆盖或暂存整个工作区。

执行最小相关验证，并完成项目要求的检查。根据实际影响、失败或尚未消除的疑虑决定是否扩大范围；相关检查通过且没有新改动时，不机械重复运行或无止境扩大测试。

验证失败时先判断原因：本次回归应修复；既有问题或环境问题要给出区分依据，不擅自扩大任务处理无关问题。重试应伴随新证据或具体修正；若无法继续，保留成果并说明阻塞和下一步。

## 续作与交接

跨轮继续时，先对照最新用户要求、已有记录、工作区及相关代码，确认什么已经完成、什么发生了变化。沿着仍然有效的下一步继续，不从头重做已完成事项。

验证结果与被验证的文件状态相关。代码、依赖或环境改变，或者旧结果不清楚时，再跑最小必要检查；未改变且有明确记录的通过结果可以复用。阻塞条件未变化时，也不反复运行同一条必然失败的命令。

任务需要中断或交接时，留下最小可恢复记录：已完成内容、当前状态、验证结果、阻塞及下一步。有计划就更新原文件；简单任务可以写在对话中，不为一次中断强制创建长期文档。命令记录注明必要的工作目录及实际结果，让下一位能直接继续。

## 完成与提交

结束前查看最终差异，确认目标已实现、相关文档已同步、必需检查已执行，并且没有混入调试产物或无关改动。简短说明结果、验证和仍然存在的实际限制。

用户已要求提交，或适用项目规则明确要求提交且未与用户要求冲突时，完成验证后只提交本任务相关改动。沿用已确认的授权，不重复询问；不要使用无差别暂存把已有用户工作一起纳入。

没有提交要求时，保留可审阅的工作区修改即可。提交、推送、合并和部署是不同动作，不由本技能自动捆绑执行；按照当前任务已有的授权范围处理。
