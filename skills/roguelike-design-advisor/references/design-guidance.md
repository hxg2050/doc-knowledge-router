# 设计取舍

按当前问题选用本页，不需要把这些检查逐一展示给用户。

## 找方向：先改变玩家行为

当用户只提出主题，例如“火焰技能”，优先比较玩法方向：追击留痕、持续叠加后兑现、击杀后传播。它们分别强调路线、时机和目标顺序；换名字或换元素并不构成新的方向。

当游戏主要自动攻击时，可以把选择放在走位、敌群排列、拾取路线、目标优先级或局内强化，而不强制增加主动键。

初始方案先让少量机制运转。追加机制应提供可解释的行为变化或取舍；不要为了表现组合丰富而让每个技能都附带伤害、治疗、护盾、位移和控制。

## 把技能改成自动触发

先保留核心效果和组成机制，再替换触发方式。不要用“原条目是主动技能”作为排除理由。

例如「霜蚀领域」使用持续作用区域、行动减速和周期伤害。可以主动选点，也可以定时在附近敌群中生成，或受击后出现在自身周围。前者更精准，后两者更自动化；是否进一步调整范围和频率，由当前游戏决定。

只在影响方案成立时说明：

- 原本由玩家选目标或落点，自动版本需要一个简单且可预期的选择规则。
- 原本可蓄力、遥控、二次按键确认，自动版本要把这项决定替换为事件或简短规则。
- 原本承担施放时机或打断风险，自动版本可能需要另一种代价。
- 周期启动整个技能与技能内部周期跳伤是不同规则；避免把两者误算成同一个频率。

不承诺所有技能都能无损改成被动。若核心乐趣来自精准格挡或手动瞄准，自动化后应指出体验改变，并给替代方向。

## 组合时分清三种关系

**组成**：技能确实执行的基础规则，例如「位移＋路径留痕＋周期伤害」。

**搭配**：另一个技能帮助它发挥，例如聚怪帮助火痕命中更多敌人，但聚怪不一定属于火痕技能自身。

**约束**：用来保证组合有限且可读的规则，例如多弹片触发系数、同目标命中间隔、连锁共享预算。只在出现对应问题时增加。

资料的 `mechanismIds` 表达组成，`relations` 表达参考或搭配。二者不能自动互相替换。

## 按需要检查收益与代价

| 出现的设计 | 关键问题 | 可考虑的修正 |
| --- | --- | --- |
| 分裂、弹射、持续伤害都能触发附加攻击 | 衍生事件能否继续触发自身或互相递归？ | 事件来源限制、共享预算或有限代数 |
| 消耗生命，但马上回复全部成本 | 这个玩法还承担什么风险？ | 区分支付与受伤事件，保留真实机会成本 |
| 击杀刷新、击杀成长、死亡传播 | 孤立首领时是否还具备基础能力？ | 保留基础输出，或提供较慢的非击杀启动路径 |
| 一次位移同时伤害、长无敌、治疗并全额重置 | 其他动作还有没有使用理由？ | 只保留关键收益，或让条件与代价相互制约 |
| 资源 A 转 B，再由 B 转 A | 整个闭环净收益是否为正？ | 有损转换、总量限制或不允许反向触发 |
| 所有新奖励只有百分比增伤 | 玩家是否只是越来越强，却没有新选择？ | 增加改变路径、目标、时机或资源使用的变体 |

这些是设计假设，无法代替原型测试。没有伤害、敌人或经济数据时，不把具体百分比说成平衡答案。

## 用户要求落地时再验证

挑一两个最可能推翻方案的场景。例如：清场型技能测试密集敌群和孤立首领；位移技能测试开阔场地和狭道；资源循环测试无额外掉落时能否维持。

观察实际行为与收益：是否产生预期走位或选目标，是否存在唯一最优操作，是否能通过少量组件启动。需要数值时给可调整的原型起点，并明确待验证项。

## 用户要求维护资料时

正文集中在 `library.json`，索引只保留 ID、名称、标签和摘要。新增机制的 `mechanismIds` 应为空；技能可以引用一个或多个机制。保留旧 ID，避免因为改名断开组成关系。

可选触发方式用一段 `activationOptions` 文本表达即可，不要求为每个方案填写完整参数。网页中的旧 `trigger` 与标签可以保留作为原始示例。

变更后运行：

```bash
python scripts/query_library.py --check
```

这只检查资料结构、引用和检索所需字段，不代表玩法已经通过验证。补充索引中的新条目；涉及公开使用示例时同步仓库 `examples/`。除非用户要求，不把新建议自动写回资料库。
